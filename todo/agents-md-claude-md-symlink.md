# Optional AGENTS.md / CLAUDE.md symlink pair for generated root files

## Context

selfdoc manages repository-level files (`README.md`, `.claude/CLAUDE.md`) via
templates in `.strictmetadata/docs/` with an underscore prefix
(`.strictmetadata/docs/_CLAUDE.md`), configured through the `root_files` key in
`selfdoc.json`. Generated files carry an
`<!-- Auto-generated by selfdoc from <template> — do not edit -->` header and
are chmod 444. The `_CLAUDE.md` template always generates `.claude/CLAUDE.md`,
not a root `CLAUDE.md`: see "Why CLAUDE.md goes under `.claude/`" in
`.strictmetadata/docs/root-files.md` and "Moving the generated CLAUDE.md under
`.claude/`" in `.strictmetadata/docs/layout.md`, which record that decision and
the migration that moves an older root file.

`AGENTS.md` is the cross-vendor project-instructions convention: OpenAI Codex,
Cursor, GitHub Copilot, and most other coding agents read it natively
(Codex walks it from repo root to cwd and concatenates:
https://learn.chatgpt.com/docs/agent-configuration/agents-md).

Correction to this todo's original premise, which said Claude Code reads
`CLAUDE.md` only: since Claude Code 2.1.277 it reads `AGENTS.md` when no
`CLAUDE.md` is present. `.claude/CLAUDE.md` counts as a `CLAUDE.md` for that
rule, so a project whose `.claude/CLAUDE.md` selfdoc generates gets no
`AGENTS.md` content in Claude Code unless the generated file imports it or
carries it.

rlsbl's `upload-private-paths` check refuses `AGENTS.md` as it refuses
`CLAUDE.md`: agent instructions, private at any depth, must never reach a
published upload. At a Go module's root that cannot be done by exclusion (Go
leaves only a whole directory holding its own `go.mod` out of a module zip),
and unlike `CLAUDE.md`, `AGENTS.md` cannot move under `.claude/`, because the
other agents read it at the repository root. Any design here has to answer how
a root `AGENTS.md` stays out of a Go module zip.

A project that wants to be usable by both Claude Code and AGENTS.md-reading
agents currently has to maintain the instructions file twice or hand-create a
symlink outside selfdoc's management.

## Problem

selfdoc should optionally generate BOTH names, one as the real generated file
and the other as a symlink to it, so a single template serves every agent.

## Solutions

### Option A: real `AGENTS.md`, symlink `.claude/CLAUDE.md` -> `../AGENTS.md`

The template becomes the source of the cross-vendor-standard filename; Claude
Code follows the symlink.

- Pros: the real file carries the industry-standard name; content is
  agent-neutral by framing; new agents that adopt the convention work with no
  further change.
- Cons: existing projects template `.strictmetadata/docs/_CLAUDE.md` — needs
  either a rename to `_AGENTS.md` or a mapping so the template name and output
  name can differ; a root `AGENTS.md` meets rlsbl's upload refusal in a Go
  module; Claude Code's checkpoint/rewind feature skips symlinked paths (a
  minor operational caveat, and the file is read-only anyway).
- The requester leaned toward this direction.

### Option B: real `.claude/CLAUDE.md`, symlink `AGENTS.md` -> `.claude/CLAUDE.md`

- Pros: zero change to existing template naming and generation; purely
  additive.
- Cons: the standard-named file is the alias rather than the source; content
  written with Claude-specific framing leaks to other agents unchanged; the
  root `AGENTS.md` symlink is still a committed private path at a Go module's
  root, which rlsbl's upload check refuses.

### Option C: generate both as real files from one template

- Pros: no symlink semantics to worry about on exotic filesystems.
- Cons: two copies of the same content on disk; violates the
  single-authority principle selfdoc exists for; diffs and greps hit
  everything twice. Offered for completeness, not recommended.

## Design notes

- Must be opt-in via explicit configuration (a key under `root_files` or a
  sibling key in `selfdoc.json`); no implicit default.
- The symlink is created/repaired by `selfdoc gen` and should be validated by
  `selfdoc check` (exists, points at the right target, not a stale copy).
- chmod 444 applies to the real file; the symlink itself needs no permission
  handling.
- The generated-file header stays in the real file; agents reading through
  the symlink see it, which is correct.
- Decide behavior when the non-generated name already exists as a regular
  file: hard error naming the conflict (never silently overwrite or replace
  with a symlink).

## Affected files

- Root-file generation and the `root_files` config handling in `selfdoc gen`
- `selfdoc check` validation
- Docs for `selfdoc.json` configuration

## Effort estimate

Small — a few hours including tests (symlink creation, idempotent re-run,
conflict refusal, check validation).
